## Safe image upgrade and recovery

1. Record the current image digest, PostgreSQL major and minor, collation provider/version, extensions and backup compatibility. Verify selected advisories against the candidate's exact platform digest.
2. Take a fresh full backup through the approved credential channel, verify checksums and restore it to a separate disposable database. PostgreSQL 17.12 release notes specifically call out corrupt older incremental backups and affected indexes. Review the relevant release-note repair procedures with the database owner.
3. Validate migrations, application connectivity, schema validation, authorization, Unicode and collation behavior on the candidate. Use a new volume for a base-distribution change and migrate logically. Keep the prior volume and image available. Compare representative ordered queries before any cutover.
4. Schedule a write freeze for a future cutover, test health and record counts, then resume writes after verification. Roll back to the previous instance and preserved volume only while no new writes would be lost. If writes resumed, plan reconciliation or restore the verified backup rather than switching volumes blindly. Preserve existing volumes throughout. [PostgreSQL minor upgrade policy](https://www.postgresql.org/support/versioning/) · [PostgreSQL 17.12 release notes](https://www.postgresql.org/docs/17/release-17-12.html)

The suite checks startup and health, fresh initialization and the V1–V5 upgrade, Hibernate validation, learner ownership, the 401 boundary, protected logs and request limits, Problem Details, ETags, immutable session retries, transaction rollback, legacy import and private catalog behavior. The migrations' SHA-256 checksums were compared before and after. No production database or browser-local data was used.

Frontend lint, type checking, production build, private catalog verification and formatting scoped to `frontend`, `backend`, `docs` and `README.md` passed. All 243 Vitest tests across 52 files passed with `VITEST_MAX_WORKERS=2`. The global formatting check still reports the four existing exceptions under `.github/modernize` (three generated reports) and `.vscode/settings.json`.

Controlled authentication development can use these patches with loopback, existing access boundaries and synthetic practice. Public deployment still requires production identity, review of the exact target image digest and any reachable unfixed OS advisories, a verified recovery rehearsal, and an explicit decision on Tomcat clustering. Repeat advisory and image scans on the final approved artifacts. Track OS package backports separately from server and driver releases, and remove the Maven overrides once a tested Boot BOM provides compatible fixed versions.
