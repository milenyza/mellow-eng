# Backend integration readiness

The npm workspace contains a browser-only React application. The separate Spring Boot foundation in `backend/` provides public status checks and protected learner progress, completed session and personal data contracts over PostgreSQL. Educational definitions are authored in TypeScript and shipped with the frontend. Learner records are stored locally. This document describes existing contracts and migration considerations. See [Backend architecture](backend-architecture.md) for the local service.

## Domain and ownership

| Domain            | Authored content                                                                                                            | Learner-owned records                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lessons           | Course and CEFR level contain units and lessons. Published lessons contain ordered blocks, activities and graded exercises. | Current run, stage, visits, answer drafts and submissions, explicit correction reviews, modality, active time and immutable first completion.           |
| Stories           | A story contains ordered chapters, stable paragraphs, story vocabulary and optional comprehension exercises.                | Current run and paragraph, chapter attempts and marks, first complete run, lifetime chapter IDs, reading duration and reading preferences.              |
| Games             | Game configuration, eligible vocabulary references, difficulty and Sentence Builder challenges.                             | Completed sessions, game-specific metrics, known vocabulary or challenge IDs and daily active time.                                                     |
| Practical English | Situation, phrasebook expressions, dialogues, cultural guidance and authored branching simulation graphs.                   | Completed simulation sessions with ordered choice outcomes and correction counts. Favorites from phrasebooks use the shared vocabulary store.           |
| Caderno           | Catalog vocabulary from lessons, stories, phrasebooks and editorial daily words.                                            | Favorite IDs and optional save dates, personal notes and examples, self-assigned familiarity, and completed flashcard reviews with recall observations. |
| Analytics         | Catalog indexes, labels and deterministic definitions.                                                                      | Read-only derivations from these records. The timeline, charts and reports have no storage of their own.                                                |

Course, unit, lesson, block, activity, exercise, story, chapter, paragraph, game, scenario, decision and vocabulary identifiers carry meaning across releases. Some identifiers are scoped to their parent. Lesson vocabulary uses a composite course/lesson/block/entry reference. A scenario ID is scoped to its situation. Preserve legacy IDs or retain an explicit alias when content moves. Learner projections should tolerate retired content and unresolved references. Titles and routes are display metadata and may change independently.

## Storage and validation

| Key                              | Shape                                         | Compatibility                                                                                                                                                                                               |
| -------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mellow:learner-progress`        | Versioned JSON through `ProgressRepository`   | Version 1 contains lessons and the daily ledger. Version 2 adds reading and its preferences. Version 3 adds games, version 4 adds simulations, and version 5 adds flashcards. Current writes use version 5. |
| `mellow:favorite-words`          | Unversioned list of vocabulary IDs            | The reader deduplicates IDs and accepts legacy entries without dates.                                                                                                                                       |
| `mellow:favorite-words-saved-at` | Unversioned ID-to-timestamp map               | Optional metadata. The favorite list is authoritative when the optional timestamp write fails.                                                                                                              |
| `mellow:vocabulary-annotations`  | Version 1 with records keyed by vocabulary ID | Notes, personal examples, familiarity, creation time and update time. Unknown versions enter a read-only unavailable state for editing.                                                                     |

The progress parser validates envelope versions, stable key shapes, finite timestamps and supported discriminants, answer payloads, nested attempts and completion relationships. Session parsers validate counts and identifiers, key equality and stored daily totals. Valid siblings can survive malformed story, game, simulation and card records. A malformed lesson or daily ledger can invalidate the whole envelope. Recovery uses an in-memory empty snapshot and does not write on read. An ensuing progress change can replace an invalid or unsupported envelope or serialize only recovered siblings. An import workflow needs access to the original payload before that point. Annotations enforce current limits of 1,200 characters for notes and 400 for examples and compare the current record with the editor's starting revision. Favorites and their metadata are separate keys with independent writes. Unfavoriting keeps personal study metadata and historical game and flashcard references.

All clients on the browser origin can potentially reach the same storage. It provides neither authenticated user isolation nor server-side protection, and clearing site data, a storage quota, private mode or changing browser/device can affect access. Tabs reload through storage events and the progress repository rebases before writes. This leaves races for simultaneous edits and no cross-device synchronization. Validate on the future trusted boundary and avoid logging learner text or submitted answers by default.

## Completion, timestamps and duration

- For a lesson, complete only after explicitly confirming required block visits and a correct answer or explicit correction review for every required graded activity. Keep the immutable first completion, current run and their IDs separate. Guided speaking is an ungraded visit. A replay does not increment the distinct lesson count.
- For a story, record explicit read marks and complete a run after all published chapters have been marked. Comprehension is optional. A learner can complete a chapter or story only once for accumulated coverage. The first completion and current run are the available snapshots.
- Completed games, simulations and flashcard reviews retain their session IDs. Preserve identity across retrying a write or import and use a new ID for an intentional replay. Session IDs are scoped by source when cross-module records are combined. Simulations count only completed conversations, not phrasebook or dialogue consultation. Recall labels and familiarity are self-reported and independent.
- Stored activity instants are Unix milliseconds. The browser maps them to the current local calendar for display and inclusive filters. Daily time buckets are already local calendar keys from recording time and should remain as recorded. Date-only records in a future import should carry precision explicitly. Missing instants should remain unknown. Chapter marks without dates still contribute to accumulated counts.
- The visible, focused, inactivity-gated study clock estimates active duration and splits it at local midnight. Lessons and stories share the daily ledger and must contribute once. Their time cannot be separated by day with historical data. Reconciliation of the all-time reading subtotal is possible only with a consistent ledger. Game, simulation and flashcard time comes from their completed session day buckets. Keep time and completion separate when a session crosses midnight. Per-run time can be shown only when it belongs to a retained run.
- History derives a first lesson completion and any retained finished replay, the first story completion, the latest retained dated read mark per story/chapter, and every canonical completed game, simulation and flashcard session. The first story run duration is shown with that milestone. Older overwritten runs, individual historical chapter durations and missing timestamps cannot be reconstructed.

## Migration and service seams

1. Define authenticated ownership and consent before attaching any browser data to an account. Consider multiple learners on the same browser, private or malformed storage, and unresolved content IDs.
2. Read and preserve raw envelopes before transforming. Validate with version-specific rules, report partially recoverable data, and keep the original until import is acknowledged. Agree on conflict handling for the current run, first completion, reading preferences, favorite revisions and annotations. Make repeated imports and retries idempotent.
3. Use the existing repository snapshot and subscription seam for learner progress. An API adapter would need a durable queue or explicit asynchronous operations, revision/conflict handling and separate loading/storage/sync failures. Existing synchronous `update` callbacks should not be assumed to be remote transactions.
4. Add equivalent adapters for `word-favorites.ts` and `vocabulary-annotations.ts`, keeping optional save time, conflict reporting and disabled storage states observable. Treat outcome/duration metrics and favorites as distinct data.
5. Keep domain rules in the existing lesson, reading, exercise, game and simulation services. If educational content moves to an API, preserve the catalog/content split and replace the static content loaders for curriculum, stories, phrasebooks, dialogues, simulations and vocabulary resolution behind typed interfaces. Keep publication and authorization independent. Validate writes and completions at the trusted boundary and leave analytics read-only over canonical records.
6. Confirm access control, retention, deletion and privacy requirements before operational rollout. Define time zone and precision handling before merging server and browser events. The React client still uses its local repositories. See the [completed session API](api/game-sessions.md#shared-session-contract) for the online validation and retry contract. Existing browser summaries may omit the response evidence required by the online contract. Any future import needs a separate compatibility policy that preserves this distinction.

The backend now has a relational persistence model. Review the [database design and field mappings](database-design.md) before implementing API adapters. Browser records remain the active source for the frontend.

## Personal resource migration considerations

The [favorites](api/favorites.md), [annotations](api/vocabulary-annotations.md) and [preferences](api/preferences.md) endpoints support interactive writes. The backend has a [separate import path](data-migration.md) for trusted, explicitly approved migration. Production identity, consent and browser integration remain pending. Preserve exact reference identity and deduplicate matching keys, while keeping separate meanings that share English text. Retain saved instants, date-only values or unknown dates at their actual precision. Import annotations independently from current favorite membership. Treat missing favorites and an unsupported local annotation version as distinct from a deliberate deletion.

Use per-resource revisions when adding a frontend adapter. On `412`, fetch current state and reconcile the learner's intended changes. Avoid replaying interactive additions as a way to import past favorites. Reconcile reading preferences whose local source has no modification timestamp. Keep voices and capabilities on the device. Do not discard browser data until the learner has reviewed the result and the server has acknowledged it.

## Import status

The [legacy import API](api/data-import.md) accepts the four browser learning keys and covers progress envelopes v1–v5 and annotation envelope v1. It supports dry-run planning, insert-only execution and redacted receipts. Existing conflicts and unsupported entries require acknowledgement before any eligible subset is applied. Browser storage remains authoritative until a future frontend integration explicitly coordinates migration.
