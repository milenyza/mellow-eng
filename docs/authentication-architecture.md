# Authentication architecture

This foundation runs in controlled loopback development with synthetic data. The API validates Spring Security sessions and learner ownership. Registration and email verification are available with synthetic delivery in the test suite. Credential login, identity retrieval and logout use the [authentication API](api/authentication.md). The [recovery API](api/password-recovery.md) resets passwords and revokes all prior sessions for the account. The React application continues to use its local repositories.

## Components and dependencies

The `com.mellow.backend.security` package owns the filter chain, immutable principal, Spring-backed learner resolver, CSRF bootstrap, password encoder and security Problem Details. The existing `ProgressBoundary` converts the verified identity into the `TrustedLearner` request attribute used by the educational controllers. The repositories and service ownership rules remain unchanged.

## Request authorization and learner identity

| Request                                                                                                                                                                                                                                                                            | Policy                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/status`, `GET /actuator/health`, `GET /api/v1/security/csrf`                                                                                                                                                                                                          | Public, with only these methods and paths allowlisted                                                                            |
| `POST /api/v1/auth/register`, `POST /api/v1/auth/email-verification/resend`, `POST /api/v1/auth/email-verification/confirm`                                                                                                                                                        | Public with CSRF. Registration and resend require configured verification delivery. [Account API](api/account-registration.md).  |
| `POST /api/v1/auth/password-reset/request`, `POST /api/v1/auth/password-reset/confirm`                                                                                                                                                                                             | Public with CSRF. Issuance uses the configured account mail adapter.                                                             |
| `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`                                                                                                                                                                                                                              | Public with a valid session CSRF token. Login authenticates verified credentials. Logout also accepts a valid anonymous session. |
| `GET /api/v1/auth/me`                                                                                                                                                                                                                                                              | Requires a verified learner session and `ROLE_LEARNER`.                                                                          |
| Published methods and paths under `/api/v1/lesson-progress`, `/api/v1/reading-progress`, `/api/v1/game-sessions`, `/api/v1/simulation-sessions`, `/api/v1/flashcard-sessions`, `/api/v1/favorites`, `/api/v1/vocabulary-annotations`, `/api/v1/preferences`, `/api/v1/data-import` | Verified learner and `ROLE_LEARNER`. State-changing methods also require CSRF.                                                   |
| Internal Servlet `ERROR` dispatch to `/error`                                                                                                                                                                                                                                      | Allowed to preserve safe framework error handling                                                                                |
| Other requests, including direct `/error`, `/login`, `/logout` and other Actuator paths                                                                                                                                                                                            | Denied by default                                                                                                                |

Generated users, form login, HTTP Basic, the default logout URL and saved-request redirects are disabled. The versioned JSON API uses a Spring authentication provider, explicit security context persistence and Spring logout handlers. The server only trusts an authenticated, non-anonymous Spring Security context with a `MellowPrincipal`. That immutable record carries the account UUID, learner UUID and the credential revision observed at login. Authentication state and authorities live on Spring's `Authentication`. The resolver verifies that the account is `VERIFIED`, belongs to the supplied learner and still has the principal revision. A successful password reset updates the revision in the same transaction as the hash and consumes the token. The next stale authorization check rejects the request and clears the session. An already authorized request can finish. Headers, query parameters, body fields and a client-supplied learner ID have no ownership authority. An authenticated principal with a missing, pending or mismatched account receives a generic denial. Queries and transactions still use the trusted learner and enforce existing ownership and domain preconditions.

## Server-managed sessions and CSRF

| Setting            | Behavior                                                                                                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session creation   | `IF_REQUIRED`. Public status, health and denied anonymous learner requests do not allocate sessions. The CSRF bootstrap can create an anonymous session without authentication.                                             |
| Storage and expiry | In-memory, single instance, 30 minutes of inactivity. A restart can lose all sessions. An expired or unknown identifier cannot restore authentication. Absolute lifetime and revocation policy remain future work.          |
| Cookie             | `MELLOW_SESSION`, host-only, `Path=/`, `HttpOnly`, `SameSite=Lax`, no persistent expiry, cookie-only tracking. `Secure` is enabled in the base profile. The loopback-only `dev` profile sets `Secure=false` for local HTTP. |
| Fixation           | Login invokes Spring's session ID rotation and CSRF authentication strategies and explicitly saves the verified context to the servlet session repository.                                                                  |
| Logout             | A CSRF-protected POST clears authentication and the CSRF token, invalidates the HTTP session and expires the scoped cookie.                                                                                                 |

A same-origin client retrieves `GET /api/v1/security/csrf` and receives `{ "headerName": "X-CSRF-TOKEN", "token": "…" }` with `Cache-Control: no-store`. Keep the masked token in memory and send it in that header on mutations. The expected token lives in the session. Spring's XOR masking protects the exposed token and multiple masks for the same session remain valid until renewal. Tokens supplied as query or form parameters are rejected. The client does not read the session cookie.

Share the initial token-fetch request across concurrent operations and wait for it before the first mutation. Coordinate login, logout or account changes with in-flight requests. Fetch a fresh token after successful login or logout, and discard the old account's pending writes and in-memory state. When a request gets a CSRF-specific `403`, refresh once and only repeat an operation if the identity is unchanged and its retry semantics permit it. On `401`, suspend writes and recover authentication before retrying. Multiple browser tabs need an explicit account-switch and session-expiry policy during client integration. [Spring Security 7.1 CSRF](https://docs.spring.io/spring-security/reference/7.1/servlet/exploits/csrf.html) · [Spring Security session management](https://docs.spring.io/spring-security/reference/7.1/servlet/authentication/session-management.html)

## HTTP failures, headers and origin

| Status | Problem type                                 | Meaning                                                                                                         |
| ------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 401    | `urn:mellow:problem:authentication-required` | No verified authentication, anonymous or unsupported principal, or expired/unknown session on a protected route |
| 401    | `urn:mellow:problem:session-revoked`         | The account security revision changed                                                                           |
| 403    | `urn:mellow:problem:access-denied`           | No matching verified account and learner, insufficient authority, or a default-denied route with authentication |
| 403    | `urn:mellow:problem:csrf-validation-failed`  | Expected token missing or invalid                                                                               |
| 400    | `urn:mellow:problem:request-rejected`        | Request rejected by Spring Security's HTTP firewall                                                             |

Security errors return `application/problem+json` and `Cache-Control: no-store`. Learner routes resolve identity before CSRF, so a missing or unsupported identity yields `401` even for a write with no token. An authenticated principal without a matching verified account and learner yields `403 access-denied` first. For a valid learner, CSRF precedes method authorization and controller validation. On unsupported paths, the CSRF filter can reject unsafe methods before the default authorization rule. Existing application validation, ownership, conflict, revision and not-found responses keep their current contracts.

Security writes `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`. The default HSTS writer applies only to a secure request. Protected responses and CSRF responses use `no-store`. There is no credentialed CORS policy. The backend ignores incoming forwarded headers. Future production should serve frontend assets and the API over one HTTPS origin, terminate TLS at a trusted edge, and configure HSTS and CSP for the whole origin after testing fonts, assets, scripts and navigation. Use a nonce or hash policy if needed based on the deployed React build. Configure any trusted forwarded-header boundary explicitly.

For local frontend integration, a future Vite proxy can map relative `/api` requests to `http://127.0.0.1:8080` and use the backend `dev` profile. Keep both services on loopback. No proxy or automatic API call is introduced here. [Spring Security headers](https://docs.spring.io/spring-security/reference/7.1/servlet/exploits/headers.html)

## Password encoder

The Spring `DelegatingPasswordEncoder` writes `{argon2id-v1}` and delegates to Spring's Argon2id encoder with a random 16-byte salt, a 32-byte hash, 19 MiB memory, two iterations and parallelism of one. This is an OWASP baseline. Algorithm IDs allow a future encoder to read old hashes and rehash after successful verification when parameters change. Preserve exact password characters. The credential endpoint applies the same password and body limits as registration. Login, registration, verification and password reset share the two concurrent Argon2id permits. Benchmark latency and memory with concurrent attempts before deployment. Registration stores only the versioned password encoding. [Spring password storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html) · [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## Test fixture and account rollout

PostgreSQL HTTP tests open real servlet sessions through `TestSecuritySessions`, a test-source fixture explicitly imported by the applicable test contexts. It provisions a synthetic verified account for ordinary regression fixtures and inserts a synthetic security context only on a bootstrap request using a registered one-use fixture token. The account suite also verifies that a pending account cannot be used by that context. Subsequent requests exercise the real filters, resolver, CSRF protection, ownership and controller paths with session cookies. A separate integration context verifies the fixture header cannot establish identity in the normal application. Synthetic password checks cover hash creation and verification. Session invalidation simulates an expired cookie. The account authentication suite separately registers, verifies and authenticates synthetic accounts over HTTP without injecting a principal. It covers actual cookie rotation, CSRF renewal, logout, account isolation and server-enforced expiry. Browser behavior against the future HTTPS origin remains to be tested.

1. Validate browser recovery, revoked-cookie handling and secure delivery in an explicit deployment configuration.
2. Connect the frontend after browser tests for same-origin cookie and CSRF behavior, expiry, account switching, consent and safe import. Follow the [authenticated client rollout](frontend-integration-plan.md).

Public deployment remains gated on these flows, HTTPS and reverse-proxy configuration, review of the exact PostgreSQL image and Tomcat configuration, runtime secret and database privileges, backup and restoration, and abuse monitoring. The [security remediation](security-remediation.md) records unresolved package and cluster findings.
