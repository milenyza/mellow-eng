# Legacy data migration

Mellow's import module copies supported browser-local learning records into the existing learner-owned tables. Parsing, mapping, comparison, persistence and reporting are separate. The interactive APIs remain the only route for new catalog-validated activity. The browser application retains its local repositories. A read-only export helper accepts an explicitly provided storage reader and request identifier. It does not run at startup or send network requests.

## Storage inventory

The import reads the original values from four allowlisted keys. The outer envelope preserves each value as a serialized string. A normalized browser snapshot from `parseProgress`, `restoreReading`, the history parsers or the Notebook snapshot is unsuitable for lossless import. Those readers can drop malformed siblings, add defaults, normalize preference values, deduplicate lists and omit unsupported versions.

Older versions of the progress envelope retain the same shapes for the categories they already supported. A category stored ahead of its declared version is reported. Unsupported schema versions, malformed rows, contradictory counters and unknown fields are reported without exposing raw values. Classroom references are structural IDs. Availability in today's catalog is irrelevant to import.

For lessons and stories, the import keeps recorded exercise discriminators, answers, correctness, modalities and reviewed timestamps. It never calculates new correctness from the active answer keys. When the current and first-completion snapshots share an ID but contain distinct valid state, the current version uses the existing relational run. The immutable first version is kept as a normalized supplemental snapshot on that run and returned as `legacyFirstCompletionSnapshot`. It is one milestone, so do not count its duration or attempts again. Structurally incompatible same-ID data, such as different start times, requires manual review.

The browser did not retain Word Match board attempts, complete Sentence Builder submission sequences, individual Memory Game selections, or the complete accepted/reviewed path and hints of conversations. The import records the available observations. Imported session responses expose `session.legacyImported: true` and retain a null catalog revision. Game and simulation evidence added by the interactive APIs stays null for these imports. The flag distinguishes these records from preexisting V2 rows and newer interactive sessions. Flashcard ratings remain subjective. A completed session without the timestamps required by V2 is reported as invalid. The import creates no substitute date or attempt.

Unclassified familiarity is unset in the source. Existing removed favorites and deleted annotations on the server retain their V4 revisions during import. Browser membership absence expresses no server-side delete instruction. The browser automatically materializes reading defaults and stores no per-field modification dates. A snapshot containing only defaults is therefore reported as ambiguous. A valid non-default preference may create a server row when no row exists. Missing fields take their defaults only for that newly created row. The server uses the import time as the database row update timestamp. If any preferences already exist, only equal values count as duplicates.

## Import lifecycle and conflict policy

1. Obtain explicit approval to process the learner's local data. The caller supplies one stable request identifier and sends the same raw snapshot to dry-run and execution.
2. Dry-run verifies ownership, parses the allowlisted snapshot, validates records and compares each record with current server state. It returns a plan token and report. It writes neither domain data nor receipts.
3. Execution locks the learner row, recomputes the plan against current state and compares the token. Records selected for import and the receipt commit in one transaction. A changed relevant state requires a new dry run. A failed insert leaves no persisted import.
4. Identical records are omitted from writes. Existing divergent records are conflicts. The first server-side completion, current run, tombstone, personal data or combined time entry survives. There is no last-write-wins or automatic merge.
5. The caller must explicitly accept skips if the plan has conflicts, unsupported or invalid records. The service then atomically applies the eligible subset and returns `APPLIED_WITH_SKIPS`. A successful application with no unresolved entries returns `APPLIED`, including when everything was already present.
6. Identical requests with the same ID return the existing receipt. A reused ID with different content conflicts. Different request IDs can contain overlapping snapshots. Stable learner-scoped record identities and normalized equality determine duplicates. A different session ID represents a separate replay even if its observations match.

Compare whole lesson and story aggregates, whole immutable sessions, a favorite or annotation per exact ID, a preference row and a combined date bucket. Different attempt sets inside an existing aggregate are a conflict, even if a new attempt could be added manually. Rich server-validated sessions with the same observable legacy projection remain intact, including their extra evidence. Revisions are part of the consistency check for mutable personal records. The lesson and reading comparisons use current aggregate state.

## Dates and duration

Exact browser timestamps are Unix milliseconds and map to UTC instants. Combined daily activity keys and completed-session day allocations represent the learner's local date. The import preserves them as calendar dates. Lifetime chapter IDs without associated date information retain unknown dates. Only existing exact read timestamps in run records are copied. The import does not infer a calendar day by applying a time zone to an exact instant. Future support for date-only input must preserve its precision rather than treating it as midnight. Date-only server records survive ordinary imports.

The combined day ledger contains joint lesson and reading activity. Do not split it arbitrarily, add individual run durations to it, or add the same combined bucket across exports. Equal per-day values are duplicates. Different values conflict even when the newer snapshot appears to record more time. Completed sessions retain a separate allocation whose total must equal the stored active time. Analytics can add those allocations once per canonical session ID to the combined ledger. Completion dates in the session APIs currently filter in UTC. Matching browser analytics by learner-local day will require an explicit reporting policy.

## Privacy and retention

The server processes originals in request memory, then discards them. It stores no raw dump, unrelated storage or credentials. The caller should keep the original export securely until review and any corrections finish. Receipts retain an owner-scoped summary, a fingerprint, hashed record locators, timestamps and version/status codes. They contain no notes, examples, drafts or response text. Receipts remain with the learner for retry handling and audit. Deletion of learner data in a future account lifecycle must include receipts and imported records. The current module exposes no raw-data download or receipt deletion endpoint. This keeps idempotency history without adding a second store of learner text.

A future authenticated frontend adapter should request consent, preserve the raw export without clearing local data, show the report, and ask before applying a plan with skips. It should handle stale-plan responses by refreshing and presenting conflicts. It should reconcile browser-local preference defaults and local-calendar reporting before enabling synchronization. See the [HTTP contract](api/data-import.md).
