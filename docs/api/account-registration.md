# Account registration and email verification API

The current implementation is for loopback development with synthetic addresses and passwords. Delivery is captured in the automated test suite. Account creation and verification leave the browser session anonymous.

## Account and learner ownership

Flyway V6 adds `mellow.account` and `mellow.email_verification` and an optional `learner.display_name`. The account has its own UUID, a unique foreign key to a learner UUID, original and canonical email, a password encoding, state and timestamps. The display name belongs to the learner profile. Every successful new registration provisions a fresh learner and one account. Existing learners remain unassociated, with their original IDs, records and a null display name where no value exists. No rows or credentials are seeded.

An account starts `PENDING_VERIFICATION`. Confirmation moves it to `VERIFIED` and records the verification instant. The educational APIs additionally require a Spring Security session principal with a matching verified account and learner pair and `ROLE_LEARNER`. A [password reset](password-recovery.md) can also verify a pending account by demonstrating mailbox ownership and replacing its original signup password. The database enforces unique canonical email, one account per learner, foreign keys and verification status consistency. A verified account can establish a session through the separate [login endpoint](authentication.md). Registration and confirmation themselves keep the browser session anonymous.

## Browser requests

Fetch `GET /api/v1/security/csrf` on the same origin. Retain the session cookie and submit the masked token in the returned `X-CSRF-TOKEN` header on each JSON POST below. The browser cannot read the `HttpOnly` session cookie. The local `dev` profile allows the cookie over loopback HTTP. A missing or invalid CSRF token receives `403` before the controller handles the request. Only the three POST methods below are public. GET requests cannot consume a token. Responses use `Cache-Control: no-store`. See the [session and security error contract](../authentication-architecture.md).

| Method and route                               | JSON fields                        | Success                                                                   |
| ---------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------- |
| `POST /api/v1/auth/register`                   | `displayName`, `email`, `password` | `202 {"status":"accepted"}` for new or duplicate valid submissions        |
| `POST /api/v1/auth/email-verification/resend`  | `email`, `password`                | `202 {"status":"accepted"}` regardless of whether a replacement is issued |
| `POST /api/v1/auth/email-verification/confirm` | `token`, `password`                | `204` with an empty body after a valid confirmation                       |

All fields are strings. Unknown and duplicate JSON fields are rejected, including attempts to supply roles, status, timestamps or an ownership identifier. The body limit is 4 KiB, for both known lengths and streaming input. The display name is trimmed, has 1–80 Unicode code points and excludes control characters.

### Email and password

Trim surrounding whitespace from an email and accept a practical ASCII dot-atom mailbox with a dotted DNS-style domain. Limit the address to 254 characters, local part to 64 and each domain label to 63. Quoted local parts, address literals and SMTPUTF8 addresses are outside the current policy. Preserve the trimmed original for delivery. The database key lowercases both parts using a locale-independent policy. In deployments that support internationally addressed mail or case-sensitive mailbox identities, revise this policy explicitly before enabling delivery. Dots and plus suffixes remain intact. Syntax validation is separate from mailbox control.

Passwords accept 15–128 Unicode code points, including spaces and passwords generated by a manager. Preserve the exact characters, including surrounding whitespace. Reject malformed Unicode and oversized inputs. There are no composition rules. The existing versioned Argon2id encoder stores the hash. Before real enrolment, add privacy-preserving screening against common and compromised passwords using a locally evaluated blocklist. Passwords must never be sent to an external lookup service. [NIST password guidance](https://pages.nist.gov/800-63-4/sp800-63b.html) · [OWASP email verification guidance](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)

## Verification and replacement

- The verification-specific table stores the SHA-256 digest of 32 bytes from Java `SecureRandom`. The public secret is unpadded, canonical Base64url. The raw token exists transiently in the delivery message. Each row belongs to one account, records expiry and allows only one end state. One open token per account is enforced by a partial unique index.
- `MELLOW_VERIFICATION_TOKEN_LIFETIME` defaults to `30m` and accepts one minute through one day. Confirmation requires the original signup password as well as the token. This prevents a mailbox owner from activating someone else's password by following an unsolicited link. A token can be consumed once. Invalid, expired, superseded or consumed tokens and wrong confirmation passwords share the same external error.
- Resend requires the signup password and an account still pending verification. It silently observes a one-minute cooldown based on the last issue time. A new issuance supersedes the previous token atomically. Wrong credentials, a missing account, verified accounts and cooldown all produce the same `202`. Missing candidates use a dummy Argon2id comparison kept in memory. Knowing an address alone does not let a caller repeatedly invalidate its links.
- Registration creates the learner, account and token in one transaction. PostgreSQL's canonical-email conflict handling rolls back the provisional learner on duplicates. Replacement and confirmation lock the same account row before changing token state. Concurrent requests to consume one token have at most one successful commit. A delivery exception after commit leaves the account pending. The same generic `202` is returned and a caller with the original password can request a replacement after the cooldown.

## Link origin and local delivery

`MELLOW_VERIFICATION_ORIGIN` must be an explicitly configured loopback HTTP(S) origin for this phase. Links point to `/verificar-email#token=…`. Neither `Host` nor forwarding headers participate. The future React page should read the token from the fragment, remove it promptly with history replacement, keep it only in memory, and submit it with the password and CSRF header after a deliberate user action. Keep the verification page free of analytics, third-party scripts and token-bearing logs. Email scanners can follow the link without consuming the token.

The test-only mail capture receives the branded message after the database commits and holds it in memory. It accepts synthetic `.test` recipients and never sends network mail. The normal artifact includes no adapter. Valid issuance requests return a service-wide `503` and perform no writes if no adapter or origin is configured. With an explicitly installed adapter, an individual post-commit delivery failure is logged as a generic event and offers the same resend path. A process interruption between commit and delivery has the same recovery. Before deploying, implement a vetted provider with a trusted HTTPS origin, sender authentication, secret management, bounded delivery time, abuse controls, retention and delivery monitoring. Review retry or outbox requirements before integrating it.

## Errors and abuse controls

| Status | Problem type suffix                                 | Meaning                                                                  |
| ------ | --------------------------------------------------- | ------------------------------------------------------------------------ |
| 400    | `invalid-account-input`                             | Invalid registration or resend input, or malformed JSON                  |
| 400    | `invalid-email-verification`                        | Confirmation could not be verified                                       |
| 403    | `csrf-validation-failed`                            | Missing or invalid CSRF header                                           |
| 413    | Standard Problem Details                            | Body exceeds 4 KiB                                                       |
| 415    | Standard Problem Details or `account-json-required` | Content type is not supported                                            |
| 429    | `account-rate-limited`                              | Request budget or hashing capacity exceeded. Includes `Retry-After: 60`. |
| 500    | `account-request-failed`                            | Unexpected persistence or processing failure                             |
| 503    | `verification-mail-unavailable`                     | Verification delivery is unavailable for the service                     |

A fixed one-minute window uses the servlet connection address and ignores arbitrary forwarded IP headers. Per-source limits are 8 registrations, 12 resends and 30 confirmations per window. Global limits are 60, 90 and 180 per operation, respectively. These totals bound the in-memory source maps. A shared semaphore permits two simultaneous Argon2id operations across registration, resend, confirmation, login and password reset. Rate admission happens after the bounded JSON parse and before persistence or hashing. A database-backed resend cooldown persists across restarts. Limits reset when the instance restarts, can affect clients sharing an address, and are local safeguards. Generic responses and dummy verification reduce ordinary enumeration signals. Response timing, delivery observations and address squatting remain considerations. Before opening public registration, validate pending account recovery in browsers, add edge and distributed abuse controls as appropriate, verify proxy trust and assess latency and monitoring without logging personal data.
