# Backend MVP finalization and technical audit

Audit window: 2026-11-27 to 2026-11-28. Scope includes the Java 21 modular monolith, PostgreSQL schema, authenticated integration boundary, browser storage formats, private educational rules and existing tests. The backend is suitable for the next integration stage in a controlled development environment. Production identity, vulnerability remediation and deployment validation remain gates.

## Implemented inventory

| API group                                                                                                         | Current contract                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status and health                                                                                                 | Public `GET /api/v1/status` reports the process and contract version. `GET /actuator/health` reports operational status, including the database. Other management endpoints and component details are disabled.                                                  |
| [Lessons](api/lesson-progress.md), [reading](api/reading-progress.md)                                             | Ordered aggregate lists and detail reads. A PUT writes one retained run. Strong aggregate ETags guard changed writes. Reading has explicit chapter marks and an independent optional comprehension history.                                                      |
| [Games](api/game-sessions.md), [simulations](api/simulation-sessions.md), [flashcards](api/flashcard-sessions.md) | Immutable completed sessions with canonical request digests. A repeat with the same stable ID and identical payload returns the retained view. A divergent payload conflicts. Lists filter and page scalar summaries. Details expose each module's observations. |
| [Favorites](api/favorites.md), [annotations](api/vocabulary-annotations.md), [preferences](api/preferences.md)    | Item or singleton revisions guard the mutable state. Favorite membership, learner-authored metadata and two reading preferences stay distinct. Historical vocabulary can remain unavailable in the current catalog.                                              |
| [Legacy import](api/data-import.md)                                                                               | A read-only dry run, explicit rechecked execution and an owner-scoped receipt. The browser-local repository and export helper remain independent of the service.                                                                                                 |

The learner boundary guards all nine learner-owned API groups. It obtains identity exclusively from a server-side resolver. The subsequent [authentication foundation](authentication-architecture.md) connects the resolver to Spring Security sessions and enforces CSRF. The later [account authentication flow](api/authentication.md) establishes sessions for verified accounts. Unauthenticated learner requests still return `401` and no-store responses. Database reads and writes remain scoped by the trusted learner, including child relationships. The regression suite exercises the real filter chain with synthetic sessions and verifies that spoofed query, body and header values cannot select an owner. A principal without a matching verified account and learner receives `403`. A missing owned aggregate, session or receipt receives `404`. Personal vocabulary item reads represent absence with an empty `200` snapshot and a revision. These are ownership semantics ahead of production authentication.

All APIs use explicit DTOs and controlled Problem Details. Mutable writes use `412` for a stale required revision and `428` for an absent one. Immutable collisions and stale import plans use `409`. An exact no-op or immutable retry can return the existing resource even when an earlier precondition is stale. Clients should use the documented precondition per endpoint. Personal vocabulary ETags identify mutable learner state, while publication labels can change with the catalog. Fetch vocabulary metadata afresh after a content release and use these tags for conditional writes.

The application binds to loopback by default and keeps development datasource settings in the dev profile. Database credentials come from the environment. The Compose example publishes only to loopback and requires a password. A filename and common private-key/token pattern check of the project source surfaced the documented local environment template and no matching source-embedded credential. This was a working-tree check. It did not scan ignored files or full Git history. Database exceptions are redacted in HTTP, and JDBC server error detail is disabled at the client.

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Default Jackson nesting allowed 500 levels.                                                                  | Both snapshot endpoints now reject bodies above 2 MiB, including streamed bodies without `Content-Length`. | Fill-in answers could accept NUL or an unpaired UTF-16 surrogate before attempting PostgreSQL JSONB storage.                                                                                                 | Validate the decoded free text before persistence. Accents, whitespace, valid supplementary characters and original answer text remain supported. Invalid storage characters receive `400`.                                                                                                                                                              |
| MVC DTO tracing and Hibernate entity-state tracing could expose drafts and answers under DEBUG. The latter was reproduced in the PostgreSQL regression.                                                      | Keep MVC body and handler tracing and Hibernate entity-state tracing at INFO. Keep Hibernate bound and extracted values disabled even when the application root is DEBUG. Keep infrastructure logs separate from payload logs. A regression submits and reloads a synthetic private answer under DEBUG and checks that the answer stays out of the logs. |
| Progress retry comparison consulted active grading rules first. A retired reference could make an exact retry fail even though its saved snapshot was readable.                                              | Compare retained request fields and submission observations first. A matching lesson or reading retry returns the saved view without grading it again. Any changed snapshot still follows current catalog validation and preconditions.                                                                                                                  |
| Legacy session normalization called Jackson's string accessor on numeric flashcard lengths and other unverified scalars. A supported fixed-length review or malformed sibling could abort the whole dry run. | Guard the scalar type before reading it. ## PostgreSQL integrity, locking and import

| Migration | Purpose                                                                                                                                                                                                                                           |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V1        | Application schema.                                                                                                                                                                                                                               |
| V2        | Learner-owned progress, sessions, annotations, favorites, preferences and activity ledgers. Primary and foreign keys encode ownership paths. Unique constraints and partial indexes retain one current run and one first completion per resource. |
| V3        | Request digests, catalog revisions and supplemental validated evidence for completed sessions.                                                                                                                                                    |
| V4        | Resource revisions and tombstones for favorites and annotations, plus active-list indexes.                                                                                                                                                        |
| V5        | Legacy import receipts, legacy session flags and optional, normalized first-completion JSONB snapshots for historical same-ID runs.                                                                                                               |

The audit leaves V1–V5 unchanged. The subsequent [account registration phase](api/account-registration.md) adds V6. The [recovery implementation](api/password-recovery.md) adds V7 and tests an upgrade from V6 with an existing account and learner data. Fresh initialization and the staged upgrade preserve Flyway history and legacy rows while Hibernate validates the schema. PostgreSQL tests cover duplicate and divergent immutable submissions, ownership, concurrent writes, stale updates, favorite removal and restoration, history ordering, import failures and rollback. Every domain write reviewed acquires the same pessimistic learner lock before changing subordinate records. A dry run uses a consistent read and stores no domain data or receipt. Execution reacquires current state, validates a learner-scoped plan and commits domain changes and the receipt together. No alternative lock ordering was identified. The lock deliberately serializes unrelated writes for the same learner. Measure contention with concurrent clients before changing it.

The import is insert-only, recognizes exact records across overlapping snapshots and respects existing removal markers and first milestones. Incompatible whole aggregates, missing required legacy facts, and ambiguous default-only reading preferences need human review. The service keeps only the redacted receipt and domain data. The original export is necessary to recover skipped information. See [migration design](data-migration.md) and the planned [backup workflow](frontend-integration-plan.md#backup-consent-and-recovery).

## Catalog revisions and preservation

The generator projects published frontend content into private application resources and supports `--check` to detect drift. Neither the application status nor Actuator exposes answer keys. The progress catalog has one current ruleset. Completed session writes check a separate digest advertised in the history response header. Identical completed-session retries compare their retained request digest before consulting that catalog. Imported history uses recorded observations. An exact lesson or reading retry now uses retained observations as well.

Before automatic synchronization, archive a minimal immutable _validation bundle_ per published digest as a deployment artifact. Couple the released frontend content to that digest. Pin the revision on newly opened lesson/reading runs and on queued session submissions. Retain bundles while supported active attempts reference them, with an explicit offline grace period and operational review before retirement. Only validation metadata belongs in this archive. It remains server-private and independently addressable from the presentation content. Verify deterministic output and a previous-revision resume in CI before publishing a changed bundle. Preserve a nullable or unknown provenance for older runs instead of assigning them a guessed revision.

When a pinned revision is unavailable, retain the old attempts and results, offer a read-only review of the saved state and an explicit restart on current content with a new attempt ID. Preserve offline drafts or export them for recovery. The client must surface the mismatch before advancing or applying that draft. The current implementation has no archive or per-run pinning. Changed progress still validates against the active rules, and a new completed session submitted with a retired digest receives `409`.

## Calendar scope and activity accounting

Current session query parameters `from` and `through` represent inclusive **UTC** calendar dates, implemented as `[from 00:00Z, day-after-through 00:00Z)`. The regression covers the final millisecond before UTC midnight and midnight itself. A stored local study bucket can be on a different date. For example, `2025-01-03T00:00:00Z` belongs to January 2 in America/Maceio. Existing UTC query parameters keep their meaning.

For integration, prefer an additive pair of explicit instant bounds such as `fromInstant` and `beforeInstant`, mutually exclusive with the UTC date filters. Derive those instants from the learner-selected local inclusive range in an IANA time zone, including daylight-saving transitions. The UI groups exact timestamps in that same zone. Preserve date-only and unknown record precision. Existing day allocations are the recorder's calendar dates and should be read directly. Avoid backfilling historical day keys from instants. A local study week remains Monday through Sunday.

The combined imported lesson and reading ledger has only one value per learner and day. It cannot be split. Add completed-session daily buckets once, per stable session ID, and avoid adding attempt duration to ledger totals. Interactive lesson/reading PUTs currently have no day allocation field. Resolve that accounting contract before switching the Dashboard or My Progress to server data.

## Measured performance and technical debt

On a disposable PostgreSQL 17.12 database with 10,000 synthetic game history rows, including 2,000 for one learner, `EXPLAIN (ANALYZE, BUFFERS)` used `game_history_by_learner` for a representative filtered first page of 21 rows. It hit three shared buffers. An offset of 1,900 used a bitmap index scan and sort, processing 2,000 matching rows to return 21. This confirms the owner/date index is useful and pagination with deep offsets has a cost. These are single local synthetic executions, separate from a production benchmark. The existing index and contract remain in place.

SQL traces of actual HTTP tests with shallow snapshots showed three statements for the lesson list and five for the reading list. The query shape includes a child lookup per run and additional lookups per activity or chapter containing exercises. The full aggregate lists are unpaginated. A large collection of replays can grow response size and request transaction cost, particularly during import comparison. Prefer targeted details and plan additive bounded summary endpoints plus batched child reads before serving large synchronized histories. Session history already projects summaries and leaves evidence and child collections to detail requests. No speculative index or fetch-strategy change was made.

## Reproducible builds and production gates

The default Maven target is `backend/target/`. Prior editor interference was observed under `target/classes` when an editor-generated class contained an unresolved compilation stub. The audit inspected the current class output and did not reproduce that stub. Maven can use an isolated output directory from the actual repository while the editor retains its own output. Use an absolute, newly created path to avoid writing or cleaning editor artifacts:

```sh
cd backend
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
export DOCKER_HOST="$(docker context inspect "$(docker context show)" --format '{{.Endpoints.docker.Host}}')"
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
build_dir="$(mktemp -d /tmp/mellow-maven.XXXXXX)"
./mvnw -o -B "-Dmellow.build.directory=$build_dir" verify
```

Both Maven runs from the actual repository passed 52 tests, using the normal target and a fresh isolated output directory. The tests use PostgreSQL in disposable Testcontainers and verify service startup, status, health, Flyway and Hibernate schema validation. Use the wrapper online for the initial dependency resolution and offline only with a populated cache. Avoid executing `clean` on shared editor output while builds are active. Normal test fixtures and test-only resolvers are outside the packaged main classes.

Frontend lint, type checking, build, catalog verification and application-scoped Prettier passed independently of backend availability. The first Vitest run crossed a macOS maintenance sleep of 3,646 seconds according to the power log. It reported three timing-related failures. The full suite passed on a repeat with `caffeinate -i env VITEST_MAX_WORKERS=2 npm test`, with 243 tests in 52 files in 38 seconds and unchanged timeout settings. The global formatter reports four preexisting exceptions under `.vscode` and `.github/modernize`; those files were preserved.

Before public deployment, install production identity and access controls, resolve dependency/image findings, separate migration and runtime database roles, verify database TLS and managed secrets, rehearse backup and restoration, establish learner-data retention and removal, and introduce privacy-preserving monitoring. Add authenticated account-switch and expiry tests, CSRF/origin checks, load tests with long histories and representative browsers, reviewed import recovery, calendar and active-time reconciliation, and compatibility coverage across catalog releases. Controlled test results do not establish production scale, completeness of security scanning or operational readiness. See the [integration plan](frontend-integration-plan.md).
